# Testing Approach

All tests use JUnit 5, run via `junit-platform-console-standalone.jar` (no Maven
required; see `scripts/test.sh`). Every test gets a fresh, isolated SQLite file
(`TestDb.freshDatabase()`, backed by `Files.createTempFile`), so tests never share
state with each other or with the developer's local `data/cinemareserve.db`.

## Test classes and what they cover

**`AuthServiceTest`** -- registration creates a hashed (never plaintext) password;
duplicate username/email rejected; short password rejected; correct login succeeds;
wrong password and unknown username both rejected.

**`SchedulingServiceTest`** -- valid showtime succeeds; an overlapping showtime is
rejected; two back-to-back non-overlapping showtimes are both accepted (boundary
case); an invalid time window (end before start) is rejected; a non-admin user cannot
create a showtime.

**`ReservationServiceTest`** -- an available seat can be held; a seat already held by
one user cannot be held by another; multiple distinct seats can be held together in
one reservation; a duplicate seat in the same request is rejected; an unknown seat id
is rejected; confirming a held reservation succeeds; another user cannot confirm your
reservation; an already-confirmed reservation cannot be confirmed again; an upcoming
reservation can be cancelled; cancelling frees the seat for another user; an
already-cancelled reservation cannot be cancelled again; another user's reservation
cannot be cancelled; a confirmed reservation cannot be cancelled inside the 60-minute
cancellation window; a showtime that has already started cannot be booked.

**`ReservationConcurrencyTest`** -- the centerpiece. 12 threads, each a distinct
registered user, race (via a `CountDownLatch` starting gate) to hold the same seat on
the same showtime; exactly 1 must succeed and 11 must receive
`SeatUnavailableException`, verified both by the returned results and by an
independent database query afterwards. Repeated 5 times (`@RepeatedTest(5)`). A second
test confirms booking *distinct* seats concurrently never fails on each other (the
locking strategy is not over-serializing unrelated work).

**`ReportingServiceTest`** -- the summary report counts only `CONFIRMED` tickets and
revenue, not `HELD` ones; revenue-by-movie aggregates correctly across seats; screen
occupancy percentage is computed correctly against total seat count; a non-admin
cannot access reports.

## Result
36 tests, 36 passing, 0 failing, 0 skipped -- see [test_run.txt](../../test_run.txt)
for the actual captured console output of the full suite, generated by
`scripts/test.sh` and not hand-written.

## What is *not* covered by automated tests
- The CLI layer itself (`Main.java`) is exercised only manually (see the screenshot
  list) -- it contains no business logic, only orchestration and printing, so this was
  judged an acceptable trade-off given the project's scope.
- `MovieService` and `VenueService` CRUD paths are exercised indirectly through
  `TestFixtures` (used by every other test class) rather than having their own
  dedicated test class; this is a documented gap, not a hidden one -- see
  "Future Enhancements" in the README.
